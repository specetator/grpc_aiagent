# 03 章节：实时消息推送与 Kafka 集成技术设计

## 架构概览
- 组件：`comet`（WS 接入/下行）、`logic`（鉴权/存储/路由/Kafka 产出）、`job`（Kafka 消费转发到 Comet）、`common`（配置/日志/连接池/Kafka 封装）、`proto`（RPC/消息定义）、`sql`（表结构）。
- 流程：  
  1) WS 握手：`comet` 解析 URL token → gRPC 调 `logic.VerifyToken` → 绑定 `user_id`，记录本机连接。  
  2) 上行：客户端 WS 文本 → `comet.OnTextMessage` 解析 `type`/目标 → gRPC `SendUpstreamMessage`。  
  3) 逻辑：`logic` 通过 `ConversationStore` 建会话、写 `message` 表、更新 Redis seq，生成 `ChatMessage`，按在线路由生成 `PushToCometRequest`，Kafka 产出到 `push_to_comet`。  
  4) 下行：`job` 消费 Kafka，按 comet_id 调 `CometService.PushToComet`；`comet` 在本机连接集合广播（单聊/房间/全体）。  
  5) 房间在线：`comet` 处理 `chatroom_join/leave` 控制帧 → `logic.ReportRoomJoin/Leave`，Redis 维护 `room:online_count`、`room:comets`、`room:comet_count`。

## 数据与存储
- MySQL（`sql/schema.sql`）：`user`、`session`（单聊/群聊/聊天室）、`message`、`user_session_state`、`im_group`、`group_member`。
- Redis 路由/在线：  
  - token: `token:<token> -> user_id`  
  - 用户路由：`route:user:<uid> = set<comet_id>`  
  - 会话 seq：`session:last_seq:<sid>`；已读：`user_session:read_seq:<uid>:<sid>`  
  - 聊天室路由：`room:comets:<room_id> = set<comet_id>`  
  - 在线人数：`room:online_count:<room_id>`；分布计数：`room:comet_count:<room_id>:<comet_id>`

## 核心模块
- `proto/spark_push.proto`：LogicService / CometService / JobService，`ChatMessage`、上行/下行、房间、广播定义。
- `logic`：`grpc_service`（鉴权、上行、房间上报、广播）、`conversation_store` + DAO、`redis_store`、`http_server`（登录/注册/消息/房间等演示接口）、`main`（初始化 MySQL/Redis/Kafka 并启动 gRPC+HTTP）。
- `comet`：`comet_server`（握手鉴权、帧解析、房间成员本地维护、上行转 gRPC、下行推送）、`comet_grpc_service`（接收 PushToComet）、`websocket_utils`（帧构造与上行轻量 JSON 解析）。
- `job`：消费 Kafka `push_to_comet`/`broadcast_task`，按 comet_id gRPC 下发或广播到所有 comet。
- `common`：配置、日志、MySQL/Redis 连接池、Kafka producer/consumer、线程池。

## 协议设计与原因
- 消息模型 `ChatMessage`：携带 `msg_id/session_id/msg_seq/sender_id/timestamp/msg_type/content_json/client_msg_id`，满足存储、未读、幂等与客户端重放；`content_json` 让业务负载自扩展，服务端仅补齐通用字段。
- 上行 RPC（Comet→Logic）：
  - `VerifyToken`：集中鉴权与路由登记（写 Redis `route:user:<uid>`），接入层轻量。
  - `SendUpstreamMessage`：单一入口 + `scene`（single/chatroom…）区分，逻辑层统一建会话、分配 seq、落库、入 Kafka；Comet 只做接入与转发。
  - `UserOffline`：连接清理后通知逻辑回收路由。
  - `ReportRoomJoin/Leave`：接入层上报，逻辑层维护 `room:comets` 与在线计数，保证房间粒度分片。
- 下行与任务：
  - `PushToCometRequest`：包含 `comet_id`（作为 Kafka key 保序）、`ChatMessage` 和可选 `targets`；`targets` 为空时由 comet 依据 `session_id` 前缀做房间/广播本地 fanout，减少中心展开开销。
  - `CometService.PushToComet`：让 comet 本机按连接/房间分发，避免跨节点复杂路由。
  - `Broadcast`：写入独立 Kafka 主题，job 全量下发到各 comet，防止逻辑层阻塞 fanout。
- 路由与在线：
  - 用户路由：`route:user:<uid>` set，支持多设备多连接。
  - 房间路由：`room:comets:<room_id>` + `(room, comet)` 计数，防僵尸路由；在线数 `room:online_count:<room_id>` 方便监控展示。
- 序列与未读：`session.last_msg_seq` 自增，`msg_seq` 带回客户端；`user_session_state` + Redis 缓存 read_seq/last_seq，实现 O(1) 未读计算。
- 幂等与重试：`client_msg_id`（客户端），`msg_id`（服务端）双层去重；上行返回 ACK，客户端可按 `client_msg_id` 对账。
- 房间分片策略：优先“room→comets” 切片，减少中心对全量成员展开；若无路由则回退成员全展开，保证可达性。

## 配置与端口
- `conf/logic.conf`：logic gRPC（默认 9100）/HTTP（9101）、Kafka/Redis/MySQL。
- `conf/comet.conf`：WS 端口 9000，gRPC 9105，`logic_grpc_target=127.0.0.1:9100`。
- `conf/job.conf`：Kafka 主题 `push_to_comet`、`broadcast_task`，`comet_targets=comet-1=127.0.0.1:9105`。

## 运行顺序
1) 启动依赖：MySQL、Redis、Kafka。  
2) 起 `logic`（需先 protoc/CMake 构建）。  
3) 起 `comet`（WS + gRPC）。  
4) 起 `job`（Kafka 消费转发）。  
5) 客户端：HTTP 登录获 token → WS `ws://host:9000/ws?token=...` → 发送 `single_chat` / `chatroom` 帧，收 ACK 与推送。

## 关键路径
- 上行：`comet -> logic.SendUpstreamMessage`，落库 message，seq 自增，Redis 写 last_seq；Kafka 按 comet_id 分片。
- 下行：`job` 消费 → `CometService.PushToComet` → `PushToUsers/PushToRoom/PushToAll` 本机分发。
- 房间：`chatroom_join/leave` 控制帧 → `logic.ReportRoomJoin/Leave` 维护 `room:comets`、在线人数；`room:comet_count` 精确计数。

## 可选扩展与测试
- 未读/已读：`user_session_state` + Redis 缓存；HTTP 接口可验证。
- 历史拉取：`message` 表 + `session.last_msg_seq`。
- 广播：`Broadcast` -> Kafka `broadcast_task` -> job 全 comets 推送。
- 测试要点：错误 token 拒握手；上行返回 ACK/DB 记录；在线用户下行可达；房间在线计数随 join/leave 变化；Kafka key 保序。
